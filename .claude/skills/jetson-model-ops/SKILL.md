# Installing and Testing Models and Services on a Jetson Orin Nano

Assumes: a Jetson Orin Nano 8 GB (7.3 GiB of unified memory shared by CPU and GPU) running Ollama as a systemd service, with Docker, and an agent that can run commands on the board (Claude Code on the board itself, or on another machine with SSH key access) and passwordless `sudo -n` (used by the desktop-restore steps). The measurements in `references/` come from one board (JetPack 7.2.1, Ollama 0.40.11); adapt versions, paths and container names to yours. On a board that also runs other workloads, leave it as found. Models of 7B and larger run out of memory unless the desktop is stopped.

Working rules: never delete a model; if disk is short, move files to another disk instead. Ask before anything that stops the desktop or a service the owner relies on, unless they already said to free memory, and always restore afterwards.

## Procedure
1. **Snapshot first** (one short SSH call): `free -m`, `df -h /`, `docker ps -a`, `ollama list`, `ollama --version`, `ss -ltn`. Note what already runs.
2. **Fit check before downloading.** Real file size from the Hugging Face API (`/api/models/<repo>?blobs=true`), not the repo name (a '4GB' repo shipped a 6.18 GB file; Gemma-style '4B effective' models carry large embeddings). Budget: weights + KV cache + about 1 GB runtime must fit in free memory. Measured: Q4 models up to about 3.5 GB run beside the desktop and a 1.5 GB AnythingLLM container; a 5.9 GB Q4 9B ran only with the desktop and containers stopped, a 1K context, and under 0.5 GB free at peak (it was OOM-killed with them running). Prefer official Ollama tags for the first test. For a whole list of model links, triage by size and runtime before downloading anything (see `references/model-fit-results.md`, section 'Triage of a Hugging Face link list'); most items on such lists are far too large or are not Ollama models.
3. **Large downloads over a slow link must be detached.** Run on the Jetson as `setsid nohup sh -c '<cmd>' > log 2>&1 < /dev/null &`; without `setsid` and `< /dev/null` the SSH call hangs until the client's timeout. Wrap in `until <cmd>; do sleep 5; done`. For files use `curl --http1.1 -L -C - --retry 10` (HTTP/2 stream errors dropped plain curl); verify with `sha256sum` against the repo's `SHA256SUMS`. Docker pulls resume layer by layer, so never wrap `docker pull` in a short `timeout`. Measure progress by file size over a minute, not the progress bar. Two big downloads share one slow link.
4. **Check liveness with `ps -eo etime,cmd | grep -E '[d]ocker pull|[c]url'`**. `pgrep -f` matches the SSH command line itself and reports a false 'running'.
5. **Ollama upgrade**: back up `/usr/local/bin/ollama` and `/usr/local/lib/ollama` (about 2 GB) first, then `curl -fsSL https://ollama.com/install.sh | sh` detached; models and the service override survive. Confirm `ollama --version` shows no client/server mismatch.
6. **Register models**: official `ollama pull <tag>`; Hugging Face GGUF `ollama pull hf.co/<owner>/<repo>:<QUANT>`; a local file via a Modelfile (`FROM <absolute path>`, `PARAMETER num_ctx 2048`) and `ollama create <name> -f Modelfile`. Architecture support can lag the Ollama version; `create` succeeding does not mean the load fits.
7. **AnythingLLM** (optional chat front end in Docker): setup flags, the one-loaded-model setting, switching the chat model and an end-to-end test are in `references/anythingllm.md`.
8. **Headless test for a model that does not fit** (see `references/headless-test.md`): stop the container, switch to the text console, restart Ollama, drop caches, run one short generation with a small context, then restore everything from a `trap EXIT`.
9. **Benchmark** with `scripts/ollama_bench.py <model> think|nothink <out.json> [num_ctx]`: five checkable tasks (arithmetic, JSON, trick question, format, code run against tests), tokens/s, load time, lowest free memory. Run thinking models in both modes; thinking output can eat the token budget, so a short cap truncates the answer. Make each check accept every correct form (a unit-sensitive check marked a right answer wrong), and read the failing answers before calling a model weaker. To run a whole queue unattended, chain pull then bench per model in one detached script on the Jetson and read its log and the benchmark's JSON result files; run the headless-only model last, with the restore in a `trap`. Measured results and what fits: `references/model-fit-results.md`.
10. **Report** honestly: tag and size, tasks passed, median tokens/s, lowest free memory, any OOM or error, and what was not tested. Vendor benchmark scores are directional; five tiny tasks show competence and speed, not quality.

## Pitfalls
- `systemctl isolate multi-user.target` also stops `ollama` (its unit is wanted by the default target): start it again with `sudo -n systemctl start ollama` and wait for the port before testing, or the test fails with a connection error.
- Stopping the desktop frees about 1.7 GB but ends the owner's graphical session; always restore with `systemctl isolate graphical.target` and `docker start`, and verify both afterwards.
- Check first for an earlier job that already did the work (container status, `ollama list`, earlier job logs) before repeating a step.
- A model that loads and answers in a headless one-shot test can still fail in real use: judge fit by free memory during a realistic run (retrieval plus chat), not by one generation.
- A fresh Jetson image has no CUDA compiler (`nvcc`); check with `ls /usr/local/cuda*/bin/nvcc`. It also has no system `cmake` and no GPU PyTorch (see `references/cuda-toolkit-and-gpu-builds.md`). Set up tools in user space only: a venv (`python3 -m venv ~/<dir>/venv`) with `pip install cmake ninja`, build C++ runtimes into separate `build` (CPU) and `build-cuda` dirs, CPU torch for small models. On a fresh or reset board without `nvcc`, report CPU numbers as a floor and ask before a system-wide CUDA install, since other workloads may share the board.
- **CUDA toolkit, once the owner approves** (see `references/cuda-toolkit-and-gpu-builds.md`): minimal `apt` install of `cuda-nvcc-13-2 cuda-cudart-dev-13-2 cuda-libraries-dev-13-2` from the JetPack repo, dry-run first with `apt-get -s install --no-install-recommends`; build GPU variants into separate `build-cuda` dirs so the CPU builds stay for comparison; confirm `nvcc --version`, Ollama and AnythingLLM afterwards before reporting.
- **Chain stages with marker files, one report per stage.** Detached scripts that wait on `*.done` markers (`while [ ! -f x.done ]; do sleep 20; done`) let setup, CPU tests and GPU tests run unattended in order without competing for CPU, memory or the single slow link. Schedule a one-shot report job per stage (cron or `at`) after the realistic finish time, and move it when an upstream stage slips; read the log first and cancel a report that a later check already answered.
